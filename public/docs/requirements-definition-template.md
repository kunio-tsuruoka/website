# 要件定義書テンプレート

> Beekle が実際の発注プロジェクトで使っている要件定義書テンプレートです。
> 空欄（〈　〉や「（記入例）」の箇所）を自社の内容に書き換えれば、そのまま開発会社との合意形成に使えます。
> 最初に書くべきは 1〜4 章の半分ほど。5 章以降は開発パートナーと一緒に詰めれば十分間に合います。
>
> 書き方の解説はこちら: https://beekle.jp/column/requirements-definition-template

- プロジェクト名: 〈プロジェクト名を記入〉
- 作成者 / 作成日: 〈氏名〉 / 〈YYYY-MM-DD〉
- バージョン: 0.1（ドラフト）

## 1. プロジェクト概要

### 1.1 目的（なぜやるか）
〈このシステムで解決したい業務課題と、なぜ今やるのかを2〜3行で記入〉
（記入例）現場が紙とExcelで在庫を管理しており、月末の棚卸しに毎回3日かかっている。これをなくし、リアルタイムで在庫を把握できるようにする。

### 1.2 成功の定義（何が達成されたら成功か）
〈「何がどうなったら成功」と言えるかを、できるだけ検証可能な形で記入〉
（記入例）棚卸し作業をゼロにする。欠品による販売機会損失を現状より減らす。

### 1.3 スコープ（やること・やらないこと）
- やること
  - 〈今回のリリースで作るものを箇条書き〉
- やらないこと（今回は作らない）
  - 〈あえて作らないもの。ここを明示すると後の「やっぱり欲しい」を防げる〉

## 3. ユーザーストーリー

機能の手前で、必ず「誰が・何を・なぜ」を1行で書きます。
基本構文:

```
As a   〈ユーザー（誰が）〉
I want to 〈やりたいこと〉
So that  〈得られる価値（なぜ嬉しいか）〉
```

### 3.1 ペルソナ
〈想定ユーザーを3〜5人に絞って定義。役割・ITリテラシー・使う場面など〉

### 3.2 ストーリー一覧
（記入例）

```
As a   一般ユーザー
I want to 気になる商品をお気に入り登録したい
So that  後でまとめて比較・購入判断ができる
```

```
As a   店舗運営者
I want to お気に入り登録された商品の傾向を確認したい
So that  在庫補充や仕入れ判断の精度を上げられる
```

| ID | ユーザーストーリー | 優先度（作る / 後回し / 作らない） |
| --- | --- | --- |
| US-01 | 〈As a … I want to … So that …〉 | 作る |
| US-02 | 〈記入〉 | 後回し |
| US-03 | 〈記入〉 | 作らない |

> 優先度は、ビジネス価値 × 現場で使えるか × 技術コスト の3軸で「作る／後回し／作らない」を判定します（FM法）。
> ツール: https://beekle.jp/tools/scope-manager

## 4. 機能要件（EARS記法）

機能の「振る舞い」を曖昧さなく書くために、EARS の5パターンを使い分けます。
「〜できるようにする」「〜を考慮する」のような解釈余地のある書き方を避け、発火条件を前置きで明示します。

### 4.1 機能カテゴリ
〈認証 / 在庫 / 通知 … のように機能を分類して記入〉

### 4.2 個別機能の振る舞い

**パターン1: Ubiquitous（常時要件）** — 常に成り立つ振る舞い
```
システムは、〈常に満たすべき振る舞い〉すること。
（記入例）システムは、すべての通信をTLS 1.2以上で暗号化すること。
```

**パターン2: Event-driven（イベント駆動）** — 「〜したとき、システムは〜する」
```
〈きっかけとなる出来事〉したとき、システムは、〈振る舞い〉すること。
（記入例）ユーザーがログインボタンを押したとき、システムは、認証サーバーに認証リクエストを送ること。
```

**パターン3: State-driven（状態駆動）** — 「〜の間、システムは〜する」
```
〈状態〉である間、システムは、〈振る舞い〉すること。
（記入例）ユーザーがログイン済みである間、システムは、マイページへのリンクを表示すること。
```

**パターン4: Optional Feature（オプション機能）** — 「〜が有効な場合、システムは〜する」
```
〈条件・オプション〉の場合、システムは、〈振る舞い〉すること。
（記入例）二要素認証が有効な場合、システムは、ログイン後にOTP入力を要求すること。
```

**パターン5: Unwanted Behavior（望ましくない事象）** — 「〜が起きたら、システムは〜することで対処する」
```
〈望ましくない事象〉した場合、システムは、〈対処〉すること。
（記入例）認証に5回連続で失敗した場合、システムは、当該アカウントを15分間ロックすること。
```

## 付録: ユーザーストーリーと EARS の併用例

ユーザーストーリーで「なぜ」を、EARS で「振る舞い」を書きます。

**ユーザーストーリー**
```
As a   一般ユーザー
I want to パスワードを忘れた時に、メールから再設定したい
So that  問い合わせなしで自分でログインを回復できる
```

**EARS（紐づく機能要件）**
```
ユーザーが「パスワードを忘れた」リンクを押したとき、
システムは、メールアドレス入力フォームを表示すること。

ユーザーが登録済みのメールアドレスを送信したとき、
システムは、1時間有効な再設定リンクを当該メールアドレスに送付すること。

入力されたメールアドレスが未登録の場合でも、
システムは、登録の有無にかかわらず同じ完了メッセージを表示すること
（「該当メールアドレスは登録されていません」とは表示しない）。
```

3つ目の「望ましくない事象」の要件が、アカウントの存在確認攻撃を防ぐ実装意図を伝えています。
機能リストだけを書いていると抜け落ちる情報です。

このように書いた EARS 要件は、そのまま Gherkin 形式（Given / When / Then）のテストシナリオに変換でき、受入条件＝テストとして使えます。
